      解析：事件 → 发送任务

      步查什么得到
      1 定受众事件目录员工 / 客户 / 双方
      2 取策略医院配置，没有取集团开关、通道顺序、收件角色、时点、重试
      3 选通道身份绑定 + 通道顺序第一个可用通道
      4 选模板事件码 × 渠道模板与渲染好的内容快照；未绑定则不发该通道，记「模板未配置」
      5 生成任务以上结果发送计划

      第 4 步没有「医院覆盖」：模板由集团指定，医院配置里不出现模板项。

      模板只按「事件码 × 渠道」绑定，不再带账号维：每个渠道在部署配置里固定一个发送账号（见 §3.5），模板天然归属该渠道的账号。

      通道

      通道受众营销回执限制
      企微应用员工否无每人每分钟 30 次；四种消息类型见下
      群机器人员工（本院群内）否无每分钟 20 条；群 webhook 与 @ 名单属员工接收人，本院自己配
      服务号模板客户否有有公众号标识即可发
      小程序订阅客户否有一次性额度
      短信客户是有70 字含签名；须平台报备模板

      规则：员工通道默认走企微应用，群机器人是本院可选的第二条员工通道（一家医院一个群），两者都没有短信兜底；客户默认服务号 → 订阅 → 短信；营销只走短信。

      企微应用只做四种消息。 文本、文本卡片、图片卡片、markdown——四种字段不通用，模板里选定一种，预览与校验跟着变。应用消息是点对点发给收件人的，没有 @ 概念。

      群机器人只做两种消息。 文本、markdown。群与 @ 人不在模板里配，也不放集团层：每家医院的群不一样、要 @ 的人也不一样，所以它归在员工接收人里——医院管理员在本院配置的「员工接收人」中填本院的群 webhook 与 @ 名单，保存即生效；集团层没有群账号，也不随部署下发。员工通知默认仍走企微应用。

      渠道消息类型必填字段上限
      企微应用文本正文2048 字节
      企微应用文本卡片标题、描述、跳转链接、按钮文字标题 128、描述 512 字节
      企微应用图片卡片标题、描述、图片、跳转链接图片 640 × 320
      企微应用markdown正文4096 字节；支持标题、加粗、三种字体色、引用、链接，不支持表格
      群机器人文本正文2048 字节
      群机器人markdown正文4096 字节

      除群 webhook 外，发送账号不在后台维护。 短信签名、服务号、订阅、企微应用各固定一个发送账号，账号与凭证引用随部署配置下发（KMS 的 key id 或环境变量名），由运维随发布管理；后台不提供维护入口，也不显示密钥，只显示账号名。轮换密钥只改部署指向，不动配置、不动代码。群机器人没有平台账号，只有本院群的 webhook，它归员工接收人，见 4.2。

      回执与结果回调

      情况处理
      明确失败（未关注、无额度、号码无效）降级到下一通道
      用户拒收不重试、不降级
      暂时失败（超时、限流、5xx）同通道重试 1/5/30 分钟，最多 3 次
      已受理无回执停，不补发，不显示已送达
      全部不可用进失败队列，原因「无可用通道」

      结果回调（服务 → 业务系统，本期做）：

      • 任务进终态（成功 / 降级后成功 / 最终失败）时回调一次，不逐条通道回调。
      • 内容：任务号、事件编号、终态、实际通道、失败原因码、发生时间。
      • 地址在调用方接入配置里登记，一个调用方一个地址；带签名与时间戳。
      • 回调失败按 1/5/30 分钟重试 3 次，仍失败入库，按需重推（无界面）。
      • 业务系统按任务号去重，重复回调不重复处理。
      • 业务系统不必轮询任务查询接口；轮询只留给对账与排查。

      应用层

      配置怎么生效

      • 事件字典由集团统一维护，默认全部开启；医院只决定两件事：本院开不开这个业务、开启后发哪些事件码。
      • 医院配置以医院为维度：一家医院一条记录。列表默认是空的——没有记录就全部沿用集团默认，不预先给每家医院生成一份。
      • 新增配置时，页面里列出所有事件与每个事件的具体事件码，每一项的默认值就是集团配置；医院只改要差异化的项，没动的继续跟集团走。
      • 同一医院、同一事件下只有一条覆盖记录。
      • 集团锁定项：短信签名、模板。医院不可改，页面不出现编辑入口。
      • 群 webhook 与 @ 名单不是账号项，是员工接收人的一部分：每家医院的群不一样，所以配置权在医院、在员工维度，集团层没有这一项、也不随部署下发；填完只显示末 8 位，改动进流水。
      • 改配置只影响新任务，已生成任务按原计划执行。
      • 保存时可勾选同步院部，把同一份配置一次写到多个院部，写入选中的即覆盖，见 4.2。

      配置项

      按回答什么问题分组，医院不能自造配置项。

      回答什么配置项
      发不发事件开关 + 事件码开关（粒度到事件码）
      发给谁（员工维度）固定角色、指定个人、本院群 webhook 与 @ 名单（群账号只在这里配）
      发给谁（客户维度）客户本人，固定不可改，没有抄送
      走哪条通道员工：企微应用 / 群机器人；客户：服务号 → 订阅 → 短信 的顺序
      什么时候发发送时点：事件发生即发 / 定时 / 事件前 N 小时
      什么时候不发免打扰时段，紧急通知可穿透
      失败怎么办重试次数、失败告警接收人

      这七项按事件单独配：同一家医院里，改约的接收人不等于爽约的接收人，发送时点与免打扰也各配各的，没有医院级全局项。受众是「双方」的事件，员工与客户两个维度都要配；只发员工或只发客户的事件，另一个维度置灰不生效。

      医院能配的只有：开关、接收人（含群 webhook 与 @ 名单）、通道顺序、时点、免打扰、重试，外加保存时一次性选择的同步院部。签名与模板是集团常量，其余账号随部署配置。

      员工收件人在配置这条消息时手工勾选，不接通讯录、不做同步：

      类型取值
      固定角色前台、核销员、院长、运营，可多选
      指定个人管理员或其他个人，可多选
      本院群一条群 webhook + @ 名单若干，只在群机器人通道生效，这就是群账号本身
      客户本人事件里的客户，固定不可改；不支持抄送、代收

      同步院部。 保存本院配置时，可在页脚勾选把这份配置一并写到其它院部（可多选）。写入即覆盖所选院部在该事件上的原有配置；没勾的院部不受影响。同步是一次性的保存动作，不是一条常驻配置项，所以它不挂在事件树上、也不进分节。

      情形结果
      全部员工有权限所选院部整份写入，覆盖原有同事件配置
      部分员工无权限员工通知跳过并逐个列出，客户通知与其余项照常写入
      一个都没勾只写本院，其它院部不动
      覆盖撤销不做撤销，要恢复只能重新配一份

      谁被校验：勾选的角色按目标院部展开到人，指定个人要有目标院部的数据权限；不满足的列到人，不让整次保存失败。

      临时通知（名单群发）

      不是事件驱动，是人在后台发起。停诊、活动、系统维护这类一次性通知。

      项做法
      入口临时通知列表：一行一条通知，可新建、发布草稿、看记录明细
      名单只支持导入表格（手机号 / 客户 ID / 员工），一次一份
      谁能发按后台角色权限控制，有「临时通知」权限的角色才能进
      账号不选，用集团账号
      内容唯一可选模板的地方：发送人从集团已审核模板里选一个，变量按名单列映射
      提交前核对人数、去重后人数与预计计费条数，勾选确认才能发布
      上限不设，导入多少发多少
      结果一个批次号，记录明细看逐人状态，可导出；不单独做批次结果页

      与事件的区别：没有业务单号、不参与乱序判断，按「批次号 + 收件人」去重；复用同一套任务、通道、回执、失败队列。

      后台菜单

      菜单维护什么谁用
      模板管理按渠道分型维护：短信 / 服务号 / 订阅 / 企微应用（四种消息类型）/ 群机器人（两种消息类型），各自的字段、变量映射、预览、测试发送模板管理员
      事件与策略事件字典（业务域 → 事件 → 事件码）、集团默认模板、启停；不提供编辑策略入口集团管理员
      医院配置以医院为维度：新增配置后逐事件覆盖集团默认（接收人、通道、时点、免打扰、重试、群 webhook 与 @ 人）；保存时可勾选同步院部医院管理员

      两张字典表，都在集团层维护：

      表一行是什么关键字段
      事件字典一个事件码事件名称、事件码、业务域、受众、必填字段、变量 schema、实现方式、默认模板、启停
      模板一个渠道 × 事件码的模板渠道类型、平台模板 ID（短信 / 服务号 / 订阅 必填）、事件码、变量映射与兜底

      事件码怎么加，代码怎么认

      事件码不是自由文本，是代码契约。服务端有一张「事件码 → 处理器」注册表，启动时加载；接入一条事件时查两处：字典里有、注册表里也有，才处理。

      类型谁能加代码里有什么后台能做什么
      业务事件只能研发注册处理器：解析受众、取业务数据、算时点启停、绑模板、改必填校验
      纯转发事件集团管理员可加无处理器，只做变量 → 模板 → 发送新增、定义变量 schema、自测通过后启用
      • 业务域只是分类标签，用于后台分组和权限范围，不参与运行时判断；代码不认识「业务域」字符串。
      • 事件码必须 <业务域前缀>_<动作>，前缀须在业务域表里存在；1234 这种直接拒绝。
      • 纯转发事件必须定义变量 schema（变量名、类型、必填），否则模板里的变量取不到值，自测过不了、启用不了。
      • 字典有、注册表没有 → 接入返回 422「事件未实现」，不静默成功。

      模板按渠道分型

      短信看平台模板 ID、签名与字数；服务号看模板 ID 与槽位；订阅看模板 ID 与跳转页；企微应用先在文本 / 文本卡片 / 图片卡片 / markdown 里选一种再填字段；群机器人只在文本与 markdown 里选一种，群与 @ 人不在这里。五类字段不通用，一张表套不住所有渠道。

      模板不存版本号。 一个渠道 × 事件码只有一份当前模板，改完保存即生效，前后值进变更流水（操作人、时间、对象、前后值），要追溯查流水，不在后台翻版本。

      正文与变量怎么配。 自由文本渠道（短信 / 企微应用 / 群机器人）正文可编辑，变量从「插入变量」里选，只能选本事件契约里的字段，不能手写；平台模板渠道（服务号 / 订阅）正文由平台模板决定，本页只把槽位映射到事件字段。每个变量可填一个空值兜底：事件字段为空时用它，兜底也空则该变量渲染为空白，预览里报红，处理完才能保存。所以兜底不是「默认模板文案」，是「这一句在没有值时显示什么」。

      预览看三样东西。 一样张：按当前模板与示例数据渲染出的实发样子（含字数与计费条数）；二取值：每个变量渲染成什么值、来源是事件值还是兜底；三校验：字数、变量是否齐全、平台模板参数个数是否匹配、通道是否启用。预览只用示例数据，不真实发送、不占额度。

      任务、投递、失败、审计只入库，不建界面；查数据走库或 BI。
